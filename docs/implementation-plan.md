# 信用证合规审查桌面应用 —— 实施方案

> 状态：已按用户答复修订（出口企业交单前自查 / 单机 Windows / 允许外部 LLM / 支持上传手册 / 无真实样本）。见第 11 节。

## 1. 目标与范围

**目标**：出口企业人员导入信用证（L/C）及拟交单据后，系统自动提取要素、按规则逐项核对，输出带依据的不符点清单，并由人工复核、确认，最终生成审单报告。

**业务范围（第一期）**
- 依据：UCP 600、ISBP 745（国际标准银行实务）；预留 ISP98、URDG、行内细则的扩展位。
- 信用证来源：SWIFT MT700/MT707（文本报文）、PDF/扫描件。
- 交单单据：商业发票、海运提单、保险单、装箱单、原产地证、汇票，以及其他信用证要求的单据（如检验证、受益人证明）。
- 审查维度：单证相符（单据 vs L/C）、单单相符（单据 vs 单据）、时间类（装运期、交单期、有效期）、金额与数量（含溢短装条款）、签署/正本份数、单据名称与措辞。

**不在第一期**：直接对接 SWIFT 网络收发报文、核心银行系统记账、移动端。

## 2. 核心设计原则

1. **判定必须确定、可复现、可审计。** 合规结论只能由规则引擎给出，不由大模型直接下结论。AI 仅用于（a）扫描件/非结构化单据的字段抽取，（b）不符点的文字解释草稿。每条不符点都能追溯到：规则编号 → 条款依据（如 UCP600 第 14 条 d）→ 来源单据的具体位置（页码+坐标高亮）。
2. **人在回路。** 抽取结果可编辑，不符点由使用者确认/驳回/标记已知悉，全部留痕。
3. **数据不出域可选。** 默认全部本地处理；LLM/OCR 支持「本地模型 / 行内私有化服务 / 关闭」三档，由管理员策略控制，外部云服务默认禁用。
4. **规则数据化。** 规则以版本化的声明式配置 + 代码插件两层实现，规则库可独立升级，每份审单报告记录所用规则库版本。

## 3. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 桌面壳 | Electron + TypeScript | 本机已有 Node 24；Windows 企业分发成熟（MSI/自动更新）；PDF 预览生态好 |
| 前端 | React + Ant Design + PDF.js | 企业级表格/表单组件完备；PDF 高亮溯源 |
| 业务核心 | TypeScript 独立包 `@lc/core`（规则引擎、解析器、模型），与 UI 无依赖 | 可单测、可复用于将来的服务端形态 |
| 文档/OCR 服务 | Python 3.12 sidecar（FastAPI，本机回环端口，随应用打包） | PDF 解析、OCR（PaddleOCR/Tesseract）、版面分析在 Python 生态最强 |
| 本地存储 | SQLite（SQLCipher 加密）+ 文件库（加密附件） | 单机开箱即用 |
| 企业模式 | 可选连接中心服务（PostgreSQL + 对象存储）做用户、规则库、审计集中管理 | 第二阶段实现；第一期接口先抽象好 |
| 测试 | Vitest、Playwright（Electron E2E）、pytest | |
| 打包 | electron-builder（MSI + 代码签名）、PyInstaller 打包 sidecar | |

> 备选：若行内标准为 .NET/WPF 或 Java，需调整；本机未装 .NET SDK，Java 为 1.8，故默认走 Electron。

## 4. 总体架构

```
┌──────────────────────── Electron ────────────────────────┐
│ Renderer (React)          Main 进程                        │
│  案件列表 / 审单工作台  ←IPC→  应用服务层                    │
│  PDF 溯源视图                  ├ @lc/core 规则引擎·解析·模型  │
│                                ├ 存储层 (SQLite/Repo 接口)   │
│                                ├ 审计日志 / 权限 / 配置策略   │
│                                └ Sidecar 客户端 ──HTTP(127.0.0.1)─┐
└───────────────────────────────────────────────────────────┘      │
                                              Python sidecar：PDF 文本/版面、OCR、(可选)LLM 抽取适配器
```

**审查流水线**（每个案件）：
`导入 → 文档分类 → 字段抽取（含置信度）→ 人工校对 → 标准化 → 规则执行 → 不符点生成 → 人工复核 → 报告导出`

## 5. 核心模块设计

### 5.1 信用证解析（`@lc/core/lc`）
- MT700/MT707 解析器：按 SWIFT 字段标签（20、31C、31D、32B、39A、41A、42C、43P/43T、44A–44F、45A、46A、47A、48、49、50、59、71B、78 等）解析，47A/46A/45A 内的条款拆成「条款条目」。
- 条款理解：把 46A 中的单据要求（如「3/3 original B/L marked freight prepaid」）结构化为 `DocumentRequirement { 单据类型, 正本数, 副本数, 必须内容[], 签署要求 }`；无法确定性解析的条款标记为「需人工判定」，不猜。
- 修改书（MT707）按序叠加，生成「当前有效 L/C」视图并保留版本链。
- 非 SWIFT 的 PDF 版 L/C：走抽取流程后进入同一结构化模型。

### 5.2 单据抽取（sidecar + `@lc/core/extract`）
- 数字版 PDF 优先直接取文字层（含坐标）；扫描件走 OCR。
- 每种单据一个抽取 schema（发票：开证申请人、货描、单价、数量、金额、币种、日期、贸易术语…；提单：承运人、装运港/卸货港、装船日期、船名、On Board 批注、清洁性、份数、收货人/通知方…）。
- 抽取器接口 `Extractor`：规则/模板抽取（确定性，优先）→ 可选 LLM 抽取（需策略允许，输出必须带原文坐标引用，无引用的值丢弃）。
- 所有字段带 `value / confidence / source{page, bbox}`，低置信度字段在 UI 强制人工确认后才进入规则执行。

### 5.3 规则引擎（`@lc/core/rules`）
- 规则接口：`Rule { id, 依据条款, 适用范围, 严重级别, evaluate(ctx) → Finding[] }`。
- 第一批规则（约 80–120 条，分批交付）：
  - **UCP600**：第 14 条（单据审核标准：5 个银行工作日、与 L/C/其他单据不矛盾）、第 14(c) 条（交单期 21 日）、第 18 条（商业发票：抬头、金额不得超过 L/C、货描一致）、第 19–25 条（运输单据要点：装船批注、清洁、转运、装运日期）、第 28 条（保险单据：金额 110%、投保日期不晚于装运日）、第 30 条（数量/金额容差）、第 29 条（到期日顺延）。
  - **ISBP745**：货描逐字 vs 允许的缩写/拼写小差异、日期格式、"约"字释义、单据出单人与签署要求等。
  - 单单一致性：货描、数量、毛净重、唛头、船名/航次、提单号、装运港/目的港跨单据比对。
- 比对工具箱：金额/币种/容差计算、日期推算（含银行工作日日历）、文本规范化与模糊匹配（仅用于「提示疑点」，是否构成不符点仍由规则 + 人工确认；严格字段一律精确比对）。
- 严重级别：`不符点 / 疑点(需人工) / 提示`，防止漏报优先于误报。
- 规则测试：每条规则至少 3 个黄金用例（通过 / 不符 / 边界），用例库同时作为回归集。

### 5.4 案件与工作流
- 案件状态：`草稿 → 抽取中 → 待校对 → 待审查 → 待复核 → 已完成/已退单`。
- 双人复核（制单人/复核人分离）、不符点处理（确认 / 驳回并说明理由 / 申请放弃）。
- 批注、历史版本对比、案件重审（规则库升级后一键重跑并显示差异）。

### 5.5 报告
- 导出审单报告（PDF/Word）与不符点通知（SWIFT MT734 文本草稿 / 拒付通知模板），含规则库版本、审核人、时间戳、条款依据。

### 5.6 企业级能力
- **安全**：本地库 SQLCipher 加密，密钥由 Windows DPAPI/凭据管理器保护；附件加密；Electron 开启 contextIsolation、禁用 nodeIntegration、严格 CSP；sidecar 仅监听回环 + 随机令牌；日志脱敏。
- **身份与权限**：RBAC（审单员 / 复核员 / 规则管理员 / 审计员 / 系统管理员）；企业模式对接 AD/LDAP/OIDC SSO。
- **审计**：追加式审计日志（谁在何时对哪个案件做了什么，含修改前后值），带哈希链防篡改，可导出。
- **合规配置**：管理员策略文件（是否允许 LLM、OCR 引擎、数据保留期、导出限制）。
- **运维**：自动更新（内部更新源）、规则库独立更新通道、崩溃上报（脱敏、可关闭）、国际化（中/英）。
- **可靠性**：长任务队列、可中断恢复、数据备份/导入导出。

## 9. 质量保障

- **测试金字塔**：规则/解析单测（黄金用例）→ 抽取集成测试（样本集指标回归）→ Electron E2E。
- **度量指标**：不符点漏报率（首要）、误报率、字段抽取召回/精确、单案平均审单时间。规则或抽取改动必须在样本集上跑回归并对比指标，退化则阻断合并。
- **业务评审**：每批规则由具备单证资质的专家逐条确认，评审记录入库。
- **安全**：依赖扫描、签名构建、渗透自测（IPC、sidecar、文件解析）。

## 10. 主要风险与对策

| 风险 | 对策 |
|---|---|
| 规则解读有歧义，银行实务各异 | 规则带条款依据；歧义项标为「疑点」交人工；支持行内细则覆盖层 |
| 扫描件/手写件抽取不准 | 置信度门槛 + 强制人工确认；原件对照高亮 |
| 46A/47A 条款为自由文本，难完全结构化 | 无法确定性解析的条款不自动判定，逐条生成人工核对项 |
| LLM 幻觉影响结论 | LLM 不参与判定；抽取值必须有原文引用 |
| 样本数据敏感 | 脱敏流程；样本仅放受控位置，不进代码仓库公开分支 |
| 范围蔓延 | 规则与单据类型按批次上线，以样本指标驱动 |

## 11. 已确认事项（决策记录）

| 项 | 结论 | 对方案的影响 |
|---|---|---|
| 使用方 | **出口企业交单前自查** | 视角改为受益人：①收证后「审证」（识别无法履行/高风险条款、与合同不符之处）②交单前「审单」（找出会被银行挑出的不符点，给出修改建议）。不做银行拒付通知；MT734 去掉；双人复核改为可选。 |
| 样本 | **没有真实样本** | 用合成样本生成器造 L/C 与单据（含故意植入的不符点）做测试；抽取准确率无法在真实数据上验证，上线前须由用户逐步积累自己的案例回归。 |
| 外部大模型 | **允许调用** | 引入 LLM 适配层（**已定：DeepSeek API**，成本考虑；接口 `LlmClient` 与服务商解耦，可替换）：非结构化单据抽取、L/C 自由文本条款理解、手册规则提炼、不符点修改建议。判定仍由确定性规则 + 人工确认，LLM 输出必须带原文引用，无引用不采纳。 |
| 行内手册 | **无，但须支持用户上传手册** | 新增「知识库/手册」模块：上传 PDF/Word/TXT（公司内部审单清单、银行/客户要求、合同条款）→ 分段索引 → LLM 提炼为「候选检查项」→ 用户逐条审核启用 → 作为自定义规则集参与审单；规则带手册出处。 |
| 平台 | **仅 Windows 10/11** | 不做跨平台；使用 DPAPI（Electron safeStorage）保护密钥。 |
| 部署 | **单机** | 取消中心服务、SSO、RBAC 多角色；保留本地加密、审计日志（轻量）、备份/导出。 |

### DeepSeek 的约束与应对
- **仅文本输入，无图像/PDF 理解**：数字版 PDF 直接取文字层；扫描件必须先在本地 OCR（P2 的 Python sidecar，PaddleOCR/Tesseract）再把文字交给模型。OCR 质量直接决定扫描件的抽取质量，低置信度字段强制人工确认。
- **OpenAI 兼容接口**：`POST {baseUrl}/chat/completions`，Bearer 认证；使用 `response_format: json_object`（提示词须含 "json"，并设足 `max_tokens` 防截断）。已实现空内容、429、5xx、非法 JSON 的重试，余额不足(402)/Key 无效(401)不重试并给出明确提示。
- **模型名可配置**：模型名会随官方版本变化，默认 `deepseek-flash`；设置页提供下拉（预置 flash / chat / reasoner，并可用已保存的 Key 调用 `GET /models` 获取账户可用模型），也可手工输入，不在代码里假定版本能力。
- **幻觉防护**：抽取结果每个值必须带原文引用，引用须真实存在于源文本，金额/日期/币种另做格式与一致性校验，不通过的字段丢弃交人工填写（已实现并测试）。单据文本视为不可信数据，系统提示要求忽略其中的指令。
- 官方文档在本环境无法直接访问，接口细节依据公开资料；联调时以真实 Key 做一次冒烟验证。

### 外部 LLM 的数据安全措施
- 首次使用须明确同意；设置页可随时关闭，关闭后仅规则引擎 + 模板抽取可用。
- 发送前可选脱敏（银行账号、联系人等正则遮蔽）；本地记录「每次发送了什么」的调用日志。
- API Key 用 safeStorage 加密存储，不写入日志与报告。

### 自定义检查项两类
1. **结构化检查项**（可确定性执行，如「提单必须显示 Freight Prepaid」「发票须含合同号」）：由用户编辑或手册提炼后确认，按规则执行，结果为不符点。
2. **语义检查项**（只能靠 AI 判断）：结果只标为「疑点」，必须人工确认，不计入确定性结论。

### 范围调整（相对前文）
- 5.4 工作流简化为：`新建案件 → 导入 L/C → 审证 → 导入单据 → 校对 → 审单 → 修改清单 → 导出自查报告`。
- 5.5 报告改为「自查报告 + 单据修改清单（按单据分组，含建议措辞）」。
- 5.6 企业级能力保留：加密存储、审计日志、策略配置、备份、签名安装包、自动更新；去掉 SSO/RBAC/中心服务。
- 阶段增补：P2 增加 LLM 适配层；P3 增加「审证」规则与自定义规则集；新增「手册知识库」放在 P4。
